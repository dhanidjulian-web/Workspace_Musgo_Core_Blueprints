# DOKUMENTASI ARSITEKTUR PLATFORM INTEGRASI ZAPIER - BAGIAN 1: FUNDAMENTAL & STRUKTUR REPOSITORI
Selamat datang di dokumentasi hasil ekstraksi dan pengembangan mendalam untuk **Zapier Integration Platform**. Arsitektur ini dirancang untuk menjembatani sistem aplikasi internal Anda dengan ekosistem otomasi pihak ketiga terbesar di dunia. Dokumentasi ini disusun secara padat, komprehensif, dan terstruktur tanpa mengurangi esensi teknis dari platform aslinya.
## 1. STRUKTUR & METODE PEMBANGUNAN (BUILDING PATHWAYS)
Zapier menyediakan dua jalur utama bagi pengembang untuk merancang, membangun, dan mempublikasikan integrasi mereka ke dalam App Directory. Pemilihan jalur ini sangat menentukan tingkat kontrol kode dan fleksibilitas arsitektur software Anda.
 * **Jalur Visual Builder (Platform UI):** Merupakan lingkungan pengembangan berbasis web tanpa kode (*no-code / low-code web interface*). Jalur ini sangat ideal untuk deployment cepat, pembuatan prototipe, serta kolaborasi lintas tim yang tidak memerlukan logika penanganan data (*data transformation*) tingkat lanjut.
 * **Jalur CLI Builder (Zapier SDK):** Memberikan kendali administratif penuh (*full programmatic control*) kepada developer melalui lingkungan berbasis teks (*command-line interface*). Seluruh penanganan autentikasi, penyaringan pemicu (*triggers*), dan eksekusi tindakan (*actions*) ditulis murni menggunakan kode Node.js (JavaScript/TypeScript). Jalur CLI ini direkomendasikan untuk integrasi tingkat *Enterprise* dan sistem *Sovereign Scale*.
## 2. STRUKTUR TOPOLOGI INTEGRASI (INTEGRATION STRUCTURE)
Setiap paket integrasi yang berjalan di atas infrastruktur Zapier wajib mematuhi cetak biru komponen terpadu. Struktur ini mendefinisikan bagaimana data mengalir masuk dan keluar dari API aplikasi Anda menuju Zapier Runtime.
### Matriks Komponen Utama Arsitektur Integrasi:
 1. **Authentication (Gerbang Keamanan):** Mengatur bagaimana pengguna memberikan izin sah kepada Zapier untuk mengakses API Anda.
 2. **Triggers (Pemicu Aliran):** Komponen yang bertugas memantau perubahan data pada API Anda untuk kemudian menarik data tersebut masuk ke dalam Zapier.
 3. **Actions (Eksekutor Tindakan):** Komponen yang menerima data dari Zapier untuk kemudian mendorong, membuat, atau memperbarui objek baru ke dalam API Anda.
 4. **Searches (Pencarian Data):** Modul pencarian khusus (*lookup mechanism*) untuk menemukan data spesifik yang sudah ada di dalam sistem Anda sebelum tindakan lanjutan dieksekusi.
## 3. MEKANISME IMPLEMENTASI REPOSITORI (CLI STRUCTURE)
Bila Anda memilih jalur pengembangan berbasis kode (CLI SDK), struktur repositori proyek integrasi Anda akan memiliki pola manifestasi yang ketat. Berikut adalah visualisasi arsitektur direktori proyek Zapier CLI:
```text

│   ├── triggers/             # Direktori kumpulan modul pemicu (Polling / REST Hooks)
│   │   └── new_data.js

```
## 4. METODE DISTRIBUSI INTEGRASI (DEPLOYMENT VISIBILITY)
Sebelum sebuah integrasi dapat diakses oleh jutaan pengguna, Zapier memisahkan siklus hidup integrasi ke dalam dua status visibilitas yang dikelola secara ketat melalui dasbor pengembang:
 * **Private Integrations (Integrasi Internal):**
   Status awal saat integrasi baru dirilis. Hanya dapat diakses oleh pembuat aplikasi, tim internal yang diundang melalui *Manage Team*, atau pengguna eksternal yang mendapatkan tautan undangan (*invite link*) khusus. Cocok digunakan untuk pengujian beta atau sistem internal perusahaan.
 * **Public Integrations (App Directory):**
   Status setelah integrasi melewati proses *App Review* dan pemenuhan standar kualitas Zapier secara global. Integrasi akan dipublikasikan secara legal di direktori publik Zapier, memungkinkan jutaan pengguna global untuk mencari, mengintegrasikan, dan menyusun otomatisasi dengan aplikasi Anda tanpa batas.

# DOKUMENTASI ARSITEKTUR PLATFORM INTEGRASI ZAPIER - BAGIAN 2: PROTOKOL AUTENTIKASI SISTEM (AUTHENTICATION ENGINES)
Bagian ini membedah secara mendalam empat skema autentikasi utama yang didukung oleh runtime Zapier. Komponen ini berfungsi sebagai gerbang validasi identitas (*integrity guard*) untuk memastikan pertukaran token antara Zapier dan API aplikasi Anda berjalan aman.
## 1. API KEY & BASIC AUTHENTICATION (AUTENTIKASI STATIS)
Skema yang paling sederhana, di mana Zapier mengirimkan string token statis atau kombinasi *Username* dan *Password* pada setiap *Request Header*.
### Mekanisme Pengiriman Request (CLI Layer)
Setiap kali pengguna menghubungkan akun mereka, Zapier akan memicu fungsi test untuk melakukan validasi apakah kunci yang dimasukkan sah atau tidak.
```javascript
// Struktur src/authentication.js untuk API Key
const testAuthentication = (z, bundle) => {
  // Melakukan pemanggilan ringan ke endpoint profil/me untuk validasi
  return z.request({
    url: 'https://api.aplikasianda.com/v1/me',
  }).then((response) => {
    if (response.status === 401) {
      throw new Error('Kunci API yang Anda masukkan tidak valid.');
    }
    return response.json;
  });
};

module.exports = {
  type: 'custom', // Menggunakan penanganan header kustom
  fields: [
    {
      key: 'api_key',
      label: 'API Key',
      required: true,
      type: 'string',
      helpText: 'Dapatkan Kunci API Anda di menu Pengaturan Akun.'
    }
  ],
  test: testAuthentication,
  // Otomatis menyisipkan API Key ke setiap request berikutnya
  connectionLabel: '{{json.username}}'
};

```
## 2. SESSION AUTHENTICATION (AUTENTIKASI BERBASIS SESI)
Digunakan jika API Anda tidak mendukung kunci statis jangka panjang dan mengharuskan Zapier untuk menukarkan kredensial utama (*Username/Password*) dengan sebuah *Session Token* sementara yang memiliki masa kedaluwarsa.
### Alur Kerja (Workflow):
 1. Pengguna memasukkan kredensial di form input Zapier.
 2. Zapier melakukan *handshake* POST ke API Anda untuk mendapatkan token sesi.
 3. Token sesi disimpan di memori enkapsulasi Zapier dan disisipkan pada request berikutnya.
 4. Jika token kedaluwarsa (mendapat error 401), Zapier otomatis mengulang proses pembuatan sesi baru (*automatic re-authentication*).
## 3. OAUTH V2 AUTHENTICATION (STANDAR DE FACTO ENTERPRISE)
Protokol keamanan paling direkomendasikan untuk integrasi publik. Pengguna tidak perlu menyerahkan kredensial mereka ke Zapier, melainkan memberikan izin melalui halaman konfirmasi aplikasi Anda (*Authorization Grant Window*).
### Konfigurasi Endpoint OAuth v2 pada Zapier:
 * **Authorization URL:** Alamat halaman login aplikasi Anda di mana pengguna memberikan izin (Akses Grant).
   ```text
   https://aplikasianda.com/oauth/authorize
   
   ```
 * **Access Token URL:** Endpoint backend Anda yang digunakan Zapier untuk menukarkan code otorisasi dengan access_token dan refresh_token.
   ```text
   https://api.aplikasianda.com/oauth/token
   
   ```
### Struktur Penanganan Refresh Token Otomatis (CLI Level)
Zapier Runtime mendukung sirklus pembaruan token secara mandiri tanpa menginterupsi otomatisasi pengguna (*seamless background refresh*).
```javascript
module.exports = {
  type: 'oauth2',
  oauth2Config: {
    authorizeUrl: {
      url: 'https://aplikasianda.com/oauth/authorize',
      params: {
        client_id: '{{process.env.CLIENT_ID}}',
        redirect_uri: '{{bundle.inputData.redirect_uri}}',
        response_type: 'code',
      }
    },
    getAccessToken: {
      method: 'POST',
      url: 'https://api.aplikasianda.com/oauth/token',
      body: {
        code: '{{bundle.inputData.code}}',
        client_id: '{{process.env.CLIENT_ID}}',
        client_secret: '{{process.env.CLIENT_SECRET}}',
        grant_type: 'authorization_code',
        redirect_uri: '{{bundle.inputData.redirect_uri}}'
      },
      headers: {
        'Content-Type': 'application/x-www-form-urlencoded'
      }
    },
    refreshAccessToken: {
      method: 'POST',
      url: 'https://api.aplikasianda.com/oauth/token',
      body: {
        refresh_token: '{{bundle.authData.refresh_token}}',
        client_id: '{{process.env.CLIENT_ID}}',
        client_secret: '{{process.env.CLIENT_SECRET}}',
        grant_type: 'refresh_token'
      },
      headers: {
        'Content-Type': 'application/x-www-form-urlencoded'
      }
    },
    autoRefresh: true // Mengaktifkan siklus otomatis saat mendeteksi HTTP 401
  },
  test: {
    url: 'https://api.aplikasianda.com/v1/me'
  }
};

```
## 4. MULTI-LAYER VALIDATION & REQUEST INTERCEPTORS
Untuk memastikan token autentikasi selalu tersemat dengan benar pada setiap transaksi data keluar, Zapier menggunakan sistem pencegat (*Interceptors/Middlewares*).
Setiap mutasi request HTTP akan disaring oleh fungsi middleware global sebelum dikirimkan ke server API Anda:
```javascript
const includeAuthentication = (request, z, bundle) => {
  if (bundle.authData.api_key) {
    // Menyisipkan token ke dalam Header Authorization
    request.headers.Authorization = `Bearer ${bundle.authData.api_key}`;
  } else if (bundle.authData.access_token) {
    // Menyisipkan token hasil jabat tangan OAuth2
    request.headers.Authorization = `Bearer ${bundle.authData.access_token}`;
  }
  return request;
};

// Registrasi Middleware pada Inti Aplikasi (index.js)
module.exports = {
  version: require('./package.json').version,
  platformVersion: require('zapier-platform-core').version,
  authentication: require('./src/authentication'),
  beforeRequest: [
    includeAuthentication // Memaksa setiap request melewati modul enkapsulasi ini
  ]
};

```

# DOKUMENTASI ARSITEKTUR PLATFORM INTEGRASI ZAPIER - BAGIAN 3: TRIPPERS ARCHITECTURE (POLLING VS REST HOOKS)
Bagian ini membedah arsitektur **Triggers** pada Zapier, yaitu komponen yang berfungsi memantau perubahan data pada aplikasi Anda dan mengirimkannya ke Zapier Runtime. Zapier mendukung dua metode utama: **Polling** (Penarikan data berkala) dan **REST Hooks** (Pengiriman data instan berbasis *Webhooks*).
## 1. POLLING TRIGGERS (PENARIKAN DATA BERKALA)
Pada mekanisme Polling, Zapier akan mengirimkan permintaan GET ke API Anda secara periodik (misalnya setiap 1 hingga 15 menit, tergantung pada tier paket pengguna) untuk memeriksa apakah ada data baru.
### Karakteristik & Ketentuan Polling:
 * **Prinsip Kerja:** Zapier selalu mengharapkan API Anda mengembalikan sebuah *Array of Objects*.
 * **Penyaringan Urutan (Sorting):** API Anda harus mengembalikan data baru dengan urutan kronologis terbalik (data terbaru berada di urutan paling atas/indeks pertama).
 * **Pencegahan Duplikasi (Deduplication):** Zapier menggunakan field id unik pada setiap objek data untuk mendeteksi apakah data tersebut sudah pernah diproses atau belum.
### Implementasi Polling Kode (CLI SDK)
```javascript
// src/triggers/new_user_polling.js
const performPolling = (z, bundle) => {
  return z.request({
    url: 'https://api.aplikasianda.com/v1/users',
    params: {
      sort_by: 'created_at',
      order: 'desc' // Memastikan data terbaru berada di atas
    }
  }).then((response) => {
    if (response.status !== 200) {
      throw new Error('Gagal mengambil data dari server.');
    }
    return response.json; // Harus berupa Array, contoh: [{id: 123, name: "Dani"}, {id: 124, name: "Lyra"}]
  });
};

module.exports = {
  key: 'new_user_polling',
  noun: 'User',
  display: {
    label: 'Pengguna Baru (Polling)',
    description: 'Picu otomatisasi setiap kali ada pengguna baru terdaftar.'
  },
  operation: {
    perform: performPolling,
    // Output sample digunakan untuk memetakan variabel di antarmuka Zapier
    sample: {
      id: "usr_990011",
      name: "Dhani Yuliawan",
      email: "dani@musgo.id",
      created_at: "2026-05-18T12:00:00Z"
    }
  }
};

```
## 2. REST HOOKS INTERACTION (INSTANT WEBHOOKS)
Mekanisme REST Hooks jauh lebih efisien dibandingkan Polling karena data dikirimkan secara *real-time* langsung dari aplikasi Anda ke Zapier begitu sebuah *event* terjadi. Zapier bertindak secara pasif menunggu kiriman data (*payload delivery*).
### Siklus Hidup REST Hooks (Lifecycle):
 1. **Subscription (Pendaftaran):** Saat pengguna mengaktifkan Zap (otomatisasi), Zapier mengirimkan request POST ke API Anda yang berisi target_url (alamat Webhook unik dari Zapier). API Anda wajib menyimpan URL ini di basis data.
 2. **Execution (Pemicuan):** Saat terjadi event riil di aplikasi Anda, backend Anda melakukan POST berisi data payload ke target_url tersebut.
 3. **Unsubscription (Penghapusan):** Saat pengguna mematikan Zap, Zapier mengirimkan request DELETE ke API Anda untuk menghapus target_url dari database agar menghentikan aliran data.
### Implementasi REST Hooks Kode (CLI SDK)
```javascript
// src/triggers/new_user_hook.js
const subscribeHook = (z, bundle) => {
  return z.request({
    method: 'POST',
    url: 'https://api.aplikasianda.com/v1/webhooks/subscribe',
    body: {
      hook_url: bundle.targetUrl, // URL unik dari Zapier
      event: 'user.created'
    }
  }).then(response => response.json);
};

const unsubscribeHook = (z, bundle) => {
  const hookId = bundle.subscribeData.id; // Mengambil ID dari database webhook Anda
  return z.request({
    method: 'DELETE',
    url: `https://api.aplikasianda.com/v1/webhooks/unsubscribe/${hookId}`
  }).then(response => response.json);
};

// Fungsi pembongkar paket data saat Webhook diterima oleh Zapier
const performResume = (z, bundle) => {
  // Zapier menerima data mentah dari webhook dan membungkusnya dalam array
  return [bundle.cleanedRequest];
};

module.exports = {
  key: 'new_user_hook',
  noun: 'User',
  display: {
    label: 'Pengguna Baru Instan (REST Hooks)',
    description: 'Menerima data pengguna baru secara real-time melalui webhook.'
  },
  operation: {
    type: 'hook',
    performSubscribe: subscribeHook,
    performUnsubscribe: unsubscribeHook,
    perform: performResume,
    sample: {
      id: "usr_990011",
      name: "Dhani Yuliawan",
      event_type: "user.created"
    }
  }
};

```
## 3. PERFORM LIST (FALLBACK MECHANISM FOR HOOKS)
Zapier mewajibkan setiap pemicu berbasis instan (*REST Hooks*) memiliki fungsi perform cadangan yang mengarah ke endpoint polling standar. Fungsi ini disebut **Fallback List**.
**Fungsi Utama Fallback List:**
Saat pengguna sedang menyusun otomatisasi di layar editor Zapier untuk pertama kalinya, sistem belum mendaftarkan URL Webhook secara nyata ke backend Anda. Zapier akan mengeksekusi fungsi *fallback* ini untuk memanggil endpoint GET biasa demi mendapatkan sampel data awal agar pengguna dapat melakukan pemetaan kolom (*field mapping*).

# DOKUMENTASI ARSITEKTUR PLATFORM INTEGRASI ZAPIER - BAGIAN 4: ACTIONS & SEARCHS ENGINES (MUTASI DATA DAN LOOKUP MECHANISM)
Bagian ini membedah arsitektur **Actions** (Tindakan) dan **Searches** (Pencarian) pada Zapier CLI SDK. Komponen ini bertanggung jawab untuk memanipulasi status data (*data write/mutation*) pada server API Anda serta melakukan kueri pencarian rekaman (*lookup record*) secara dinamis.
## 1. ACTIONS ARCHITECTURE (CREATE/WRITE OPERATIONS)
Action dalam ekosistem Zapier bertindak sebagai eksekutor mutasi data. Komponen ini menerima kiriman parameter payload dari langkah *Trigger* sebelumnya, melakukan validasi tipe data, lalu mengirimkannya melalui metode HTTP POST atau PUT ke endpoint API Anda.
### Aturan Baku Desain Action:
 * **User Input Fields:** Setiap field input yang dibutuhkan oleh API Anda (seperti nama, email, atau status) harus didefinisikan secara eksplisit agar muncul sebagai form pengisian di antarmuka visual Zapier.
 * **Membongkar Konten Hasil (Response Unwrap):** Tindakan yang sukses wajib mengembalikan objek JSON tunggal yang mewakili data yang baru saja berhasil dibuat atau dimodifikasi pada sistem database Anda.
### Implementasi Unit Action Kode (CLI SDK)
```javascript
// src/actions/create_ticket.js
const performCreateTicket = (z, bundle) => {
  return z.request({
    method: 'POST',
    url: 'https://api.aplikasianda.com/v1/tickets',
    body: {
      subject: bundle.inputData.subject,
      description: bundle.inputData.description,
      priority: bundle.inputData.priority || 'normal',
      assigned_to: bundle.inputData.assigned_to
    },
    headers: {
      'Content-Type': 'application/json'
    }
  }).then((response) => {
    if (response.status !== 201) {
      throw new Error(`Gagal membuat tiket: ${response.content}`);
    }
    return response.json; // Mengembalikan objek data tiket yang berhasil dibuat
  });
};

module.exports = {
  key: 'create_ticket',
  noun: 'Ticket',
  display: {
    label: 'Buat Tiket Baru',
    description: 'Membuat tiket bantuan baru di dalam sistem support internal Anda.'
  },
  operation: {
    perform: performCreateTicket,
    // Definisi Form Input yang akan diisi oleh pengguna Zapier
    inputFields: [
      { key: 'subject', label: 'Subjek Tiket', required: true, type: 'string' },
      { key: 'description', label: 'Deskripsi Masalah', required: true, type: 'text' },
      { 
        key: 'priority', 
        label: 'Prioritas', 
        required: false, 
        type: 'string', 
        choices: { low: 'Rendah', normal: 'Normal', high: 'Tinggi' } 
      }
    ],
    sample: {
      id: "tkt_12345",
      subject: "Error Integrasi Server",
      priority: "high",
      status: "open",
      created_at: "2026-05-18T12:50:00Z"
    }
  }
};

```
## 2. SEARCHES ARCHITECTURE (READ/LOOKUP OPERATIONS)
Searches adalah komponen pemanggil kueri yang bertugas mencari data spesifik yang sudah ada di database Anda berdasarkan parameter kunci tertentu (misalnya mencari ID pengguna berdasarkan alamat email).
### Konsep Penting: Perbedaan Array Kosong vs Kesalahan
Jika kueri pencarian tidak menemukan kecocokan data apa pun di database Anda, API Anda harus mengembalikan status sukses HTTP 200 dengan **Array Kosong []**. Jangan mengembalikan error HTTP 404, karena Zapier menganggap array kosong sebagai hasil "tidak ditemukan" yang sah, sedangkan HTTP 404 akan memicu interupsi kegagalan fatal pada alur Zap kerja pengguna.
### Implementasi Unit Search Kode (CLI SDK)
```javascript
// src/searches/find_user.js
const performSearchUser = (z, bundle) => {
  return z.request({
    url: 'https://api.aplikasianda.com/v1/users/search',
    params: {
      email: bundle.inputData.email // Mencari record berdasarkan email unik
    }
  }).then((response) => {
    if (response.status !== 200) {
      throw new Error('Proses pencarian gagal pada interkoneksi API.');
    }
    // API harus mengembalikan array. Jika ditemukan: [{id: 1}], jika tidak: []
    return response.json; 
  });
};

module.exports = {
  key: 'find_user',
  noun: 'User',
  display: {
    label: 'Cari Pengguna',
    description: 'Menemukan data pengguna yang sudah terdaftar berdasarkan alamat email.'
  },
  operation: {
    perform: performSearchUser,
    inputFields: [
      { key: 'email', label: 'Alamat Email', required: true, type: 'string' }
    ],
    sample: {
      id: "usr_990011",
      name: "Dhani Yuliawan",
      email: "dani@musgo.id"
    }
  }
};

```
## 3. SEARCH-OR-CREATE PAIRING (ORCHESTRATION PATTERN)
Zapier memungkinkan pengembang untuk menggabungkan modul **Search** dan **Action** menjadi satu kesatuan alur kerja hibrida di antarmuka pengguna, yang dikenal sebagai *Search-or-Create*.
### Logika Eksekusi Pola:
 1. Zapier menjalankan fungsi *Search* terlebih dahulu (misal: mencari kontak berdasarkan email).
 2. Jika kontak **Ditemukan**, data kontak lama langsung diambil dan alur berlanjut ke langkah berikutnya.
 3. Jika kontak **Tidak Ditemukan** (API mengembalikan array kosong []), runtime Zapier secara otomatis memicu fungsi *Action* (Create) untuk mendaftarkan kontak tersebut sebagai kontak baru di database saat itu juga.
Pola hibrida ini mencegah terjadinya duplikasi data berulang pada sistem penyimpanan database Anda.

# DOKUMENTASI ARSITEKTUR PLATFORM INTEGRASI ZAPIER - BAGIAN 5: MANAJEMEN VERSI, DEPLOYMENT, DAN VALIDASI PUBLIK
Bagian penutup ini membedah siklus akhir dari pengembangan integrasi Zapier menggunakan CLI SDK. Kita akan fokus pada mekanisme pengelolaan versi (*Versioning*), pengujian otomatis (*Automated Testing*), perintah deployment terminal, serta persyaratan kepatuhan untuk melewati fase *App Review* publik.
## 1. STRATEGI MANAJEMEN VERSI (VERSIONING POLICY)
Setiap perubahan kode pada integrasi Zapier Anda wajib dikelola menggunakan sistem penomoran versi yang ketat di dalam file package.json. Zapier mengadopsi standar *Semantic Versioning* (SemVer) dengan format MAJOR.MINOR.PATCH (contoh: 1.0.0).
### Karakteristik Runtime Multi-Versi:
 * **Immutability (Sifat Kekal):** Sekali sebuah versi dideploy ke server Zapier (misal versi 1.0.0), kode pada versi tersebut dikunci secara absolut dan tidak bisa ditimpa (*cannot be overwritten*). Perubahan kode sekecil apa pun mengharuskan Anda menaikkan nomor versi (misal menjadi 1.0.1).
 * **Ketersediaan Paralel:** Zapier mengizinkan beberapa versi integrasi berjalan secara bersamaan di server produksi. Hal ini menjamin pengguna lama yang menggunakan versi 1.0.0 tidak akan mengalami interupsi kegagalan ketika Anda merilis pembaruan versi 2.0.0.
 * **Migrasi Pengguna (Deprecation):** Pengembang dapat mengalihkan (*migrate*) pengguna dari versi lama ke versi baru secara massal melalui konsol administratif pengembang tanpa memaksa pengguna mengonfigurasi ulang otomatisasi mereka dari awal.
## 2. PENGUJIAN OTOMATIS (AUTOMATED UNIT TESTING)
Sebelum melakukan proses push kode ke server produksi Zapier, Anda wajib melakukan pengujian unit lokalan menggunakan framework pengujian JavaScript (seperti Mocha) yang dikombinasikan dengan pustaka zapier-platform-core.
### Implementasi Berkas Pengujian (test/integration.test.js)
```javascript
const zapier = require('zapier-platform-core');
const App = require('../index'); // Mengimpor manifest utama aplikasi Anda
const appTester = zapier.createAppTester(App);

describe('Pengujian Validasi Integrasi Zapier CLI', () => {
  
  it('Harus sukses melakukan autentikasi API Key', async () => {
    const bundle = {
      authData: {
        api_key: 'test_secret_token_123'
      }
    };

    // Mengeksekusi fungsi uji autentikasi
    const result = await appTester(App.authentication.test, bundle);
    expect(result).toHaveProperty('id');
    console.log('[TEST SUCCESS] Autentikasi Lolos Validasi Kontrak.');
  });

  it('Harus mengembalikan array objek pada fungsi Polling Trigger', async () => {
    const bundle = {
      inputData: {}
    };

    const results = await appTester(App.triggers.new_user_polling.operation.perform, bundle);
    expect(Array.isArray(results)).toBe(true);
    if (results.length > 0) {
      expect(results[0]).toHaveProperty('id');
    }
    console.log('[TEST SUCCESS] Format Data Polling Terverifikasi Valid.');
  });

});

```

## 4. PERSYARATAN KEPATUHAN APP REVIEW UNTUK PUBLIKASI GLOBAL
Agar integrasi Anda disetujui untuk masuk ke dalam *Public App Directory* resmi Zapier, aplikasi Anda harus memenuhi kriteria kelayakan ketat berikut selama proses *App Review*:
 1. **Jumlah Pengguna Aktif Minimum:** Integrasi Anda harus berada dalam status *Private* terlebih dahulu dan memiliki minimal **3 pengguna aktif unik** (bukan akun internal pembuat) yang menjalankan otomatisasi secara sukses tanpa error selama periode pengujian.
 2. **Ketersediaan Dokumentasi Bantuan (Help Documentation):** Menyediakan tautan publik yang berisi panduan lengkap mengenai cara mendapatkan kredensial API atau token OAuth dari sistem Anda untuk memandu pengguna awam.
 3. **Ketahanan Error Handling:** API Anda harus secara konsisten menerapkan standarisasi kode HTTP. Kegagalan autentikasi wajib merespons dengan HTTP 401, dan pelanggaran batas limitasi wajib merespons dengan HTTP 429. Kegagalan menangani status kode ini akan menyebabkan integrasi ditolak oleh tim auditor Zapier.
 4. **Kelengkapan Data Sampel (Sample Completeness):** Setiap modul *Trigger*, *Action*, dan *Search* wajib menyertakan data objek sampel (*mock data*) yang lengkap dan akurat di dalam file definisinya untuk mempermudah proses pemetaan variabel oleh pengguna.
