# .gitignore Generator

Generate production-grade `.gitignore` files, audit existing ones for gaps, and validate that sensitive files, build artifacts, and OS cruft are properly excluded from version control.

## Overview

A well-crafted `.gitignore` is the first line of defense against:

- **Secrets leakage** — `.env` files, API keys, credentials, private keys
- **Build artifact pollution** — `node_modules/`, `__pycache__/`, `target/`, `dist/`
- **IDE/editor noise** — `.vscode/`, `.idea/`, `*.swp`, `.DS_Store`
- **OS-specific junk** — `Thumbs.db`, `.DS_Store`, `desktop.ini`
- **Local configuration** — user-specific settings that shouldn't be shared

This skill teaches the agent to detect project type, generate comprehensive patterns, and validate coverage.

## Execution

### Step 1: Detect Project Type

Identify the project's language(s), framework(s), and tooling by scanning for key files:

```bash
# Look for language/framework indicators
find . -maxdepth 2 -type f \( \
  -name "package.json" -o -name "requirements.txt" -o -name "pyproject.toml" -o \
  -name "Cargo.toml" -name "go.mod" -o -name "pom.xml" -o -name "build.gradle" -o \
  -name "Gemfile" -o -name "composer.json" -o -name "CMakeLists.txt" -o \
  -name "Dockerfile" -o -name "docker-compose.yml" -o -name "*.csproj" \) 2>/dev/null
```

Map detected files to project types:

| Indicator File(s)              | Project Type       |
|-------------------------------|--------------------|
| `package.json`                | Node.js            |
| `requirements.txt`, `pyproject.toml`, `setup.py`, `Pipfile` | Python |
| `Cargo.toml`                  | Rust               |
| `go.mod`, `go.sum`            | Go                 |
| `pom.xml`, `build.gradle`     | Java               |
| `Gemfile`, `Gemfile.lock`     | Ruby               |
| `composer.json`               | PHP                |
| `*.csproj`, `*.sln`           | C# / .NET          |
| `CMakeLists.txt`              | C / C++            |
| `Dockerfile`, `docker-compose.yml` | Docker         |
| Multiple of the above          | Monorepo / Polyglot|

Also check for framework indicators inside `package.json` or `pyproject.toml`:
- `next`, `react`, `vue`, `angular`, `svelte` → Frontend framework
- `django`, `flask`, `fastapi`, `pytest` → Python framework
- `terraform`, `.tf` files → Terraform

### Step 2: Scan for Sensitive Files

Before generating patterns, scan the project for files that **must** be ignored:

```bash
# Find common sensitive file patterns
find . -maxdepth 3 -type f \( \
  -name ".env" -o -name ".env.*" -o -name "*.pem" -o -name "*.key" -o \
  -name "*.p12" -o -name "*.pfx" -o -name "secrets.*" -o -name "credentials.*" -o \
  -name "*.jks" -o -name "id_rsa" -o -name "id_ed25519" -o \
  -name "*.token" -o -name ".npmrc" -o -name ".pypirc" \) 2>/dev/null
```

Check for sensitive **file contents** (not just filenames):

```bash
# Search for hardcoded secrets in source files (sample, not exhaustive)
grep -rn --include="*.py" --include="*.js" --include="*.ts" --include="*.java" --include="*.go" \
  -E "(api_key|apikey|secret_key|access_token|password)\s*=\s*['\"][^'\"]{8,}" \
  src/ lib/ app/ 2>/dev/null | head -20
```

### Step 4: Validate Existing .gitignore

If a `.gitignore` already exists, audit it for gaps:

#### 4a. Check for Tracked Files That Should Be Ignored

```bash
# List all tracked files and check against common ignore patterns
git ls-files | grep -E '\.(env|pem|key|log|pyc|class|o|so|dylib|exe|dll)$' | head -20
git ls-files | grep -E '(node_modules|__pycache__|\.venv|target/|\.idea/|\.vscode/|\.DS_Store)' | head -20
```

#### 4b. Check for Missing Common Patterns

Read the existing `.gitignore` and verify these critical patterns are present:

| Category              | Required Patterns                              |
|-----------------------|------------------------------------------------|
| Secrets               | `.env`, `.env.*`, `*.pem`, `*.key`             |
| Python                | `__pycache__/`, `*.pyc`, `.venv/` or `venv/`   |
| Node.js               | `node_modules/`, `.env`                        |
| Java                  | `*.class`, `target/` or `build/`               |
| OS                    | `.DS_Store` (macOS), `Thumbs.db` (Windows)     |
| IDE                   | `.vscode/` or `.idea/` or `*.swp`              |
| Logs                  | `*.log`                                        |

#### 4c. Check for Duplicate Patterns

```bash
# Find duplicate lines in .gitignore (excluding comments and blank lines)
grep -v '^#' .gitignore | grep -v '^$' | sort | uniq -d
```

#### 4d. Validate Pattern Syntax

Check for common syntax errors:
- Patterns with incorrect negation (e.g., `!pattern` without a prior matching pattern)
- Trailing `/` on file patterns (should only be on directory patterns)
- Incorrect use of `**` (must be used correctly for recursive matching)
- Patterns that are too broad (e.g., `*.txt` ignoring all text files)

### Step 5: Handle Already-Tracked Files

If sensitive or unwanted files are already tracked, provide remediation steps:

```bash
# Remove from Git index but keep locally
git rm --cached <file>

# Remove an entire directory from tracking
git rm -r --cached <directory>/

# Commit the cleanup
git commit -m "chore: stop tracking ignored files"
```

For files **already in Git history** (secrets exposure):
- Recommend `git filter-repo --invert-paths --path <secret-file>` 
- For older Git: `git filter-branch --tree-filter 'rm -f <secret-file>' --prune-empty -f -- --all`
- Strongly recommend rotating any exposed credentials immediately

### Step 6: Final Validation

Run a dry-run to verify the `.gitignore` catches expected files:

```bash
# Show what would be ignored (files not yet tracked)
git status --porcelain | grep '^??' | head -20

# Verify .gitignore itself is tracked
git ls-files .gitignore
```

## Quality Gates

Before declaring the task complete, verify:

- [ ] `.gitignore` file exists at project root
- [ ] All detected project stacks have corresponding pattern sections
- [ ] Sensitive file patterns are present (`.env`, `*.pem`, `*.key`, etc.)
- [ ] OS-specific files are covered (`.DS_Store`, `Thumbs.db`)
- [ ] IDE/editor patterns match the team's tools
- [ ] No duplicate patterns exist
- [ ] Pattern syntax is correct (no broken negations, correct use of `**`)
- [ ] Already-tracked sensitive files have been untracked with `git rm --cached`
- [ ] `.gitignore` itself is committed to the repository
- [ ] A comment header with generation date is present

## Common Pitfalls

### 1. Forgetting `.env` and Secret Files
The most critical omission. Always include `.env`, `.env.local`, `.env.*.local`, and language-specific secret file patterns.

### 2. Adding `.gitignore` After Files Are Already Tracked
Patterns in `.gitignore` only affect **untracked** files. Already-committed files continue to be tracked. Always check `git ls-files` and use `git rm --cached` to untrack.

### 3. Duplicate Patterns
Combining templates from multiple sources often creates duplicates. Deduplicate before committing.

### 4. Overly Broad Patterns
Avoid patterns like `*.txt` or `data/` that may catch files you want tracked. Be specific.

### 5. Missing Trailing Slash on Directories
`build` ignores files named "build" in any directory. `build/` ignores only directories named "build". Use trailing `/` for directories.

### 6. Negation Without Prior Pattern
`!important.log` does nothing unless a prior pattern like `*.log` matches it first. Negation must come **after** the pattern it negates.

### 7. `**` Misuse
`**/foo` matches `foo` in any directory. `foo/**` matches everything inside `foo/`. `**/foo/**` matches `foo` and everything inside it at any level.

### 8. Forgetting Monorepo Complexity
In monorepos, a root `.gitignore` covers all subprojects. Be careful not to ignore files needed by one subproject but not another. Consider per-subproject `.gitignore` files for stack-specific patterns.

### 9. Not Committing `.gitignore`
`.gitignore` must be committed to the repository so all team members benefit. It's not a personal file — that's what `.git/info/exclude` is for.

### 10. Ignoring Lock Files Incorrectly
- **Do NOT ignore** `package-lock.json`, `yarn.lock`, `Gemfile.lock`, `Cargo.lock` in applications (they ensure reproducible builds).
- **DO ignore** `Cargo.lock` in library projects (let consumers resolve versions).
- **DO ignore** `go.sum` only if you have a specific reason (generally keep it).
